# مهام تحليلات مستخدمي إصدارات التطبيق

## الهدف

إضافة تحليل في لوحة التحكم يوضح توزيع المستخدمين حسب إصدارات التطبيق والمنصة، بحيث يستطيع فريق الإدارة معرفة:

- كم مستخدم على كل إصدار.
- كم مستخدم على Android و iOS.
- الإصدارات القديمة أو المحظورة أو غير المعروفة.
- اتجاه الاستخدام اليومي لكل إصدار.
- قائمة المستخدمين المرتبطين بإصدار محدد.

مصدر القياس المقترح: كل طلب API مصادق عليه يرسله التطبيق، اعتمادًا على هيدرز الإصدار والمنصة.

---

## 1. مهام الباك اند

### 1.1 تتبع بيانات الإصدار من الطلبات

- توسيع `ActivityTrackingMiddleware` الحالي ليقرأ الهيدرز التالية:
  - `X-App-Version`
  - `X-App-Build-Number`
  - `X-Platform`
- ربط البيانات بالمستخدم المصادق عليه من JWT.
- تجاهل الطلبات التي لا تحتوي على `X-App-Version`.
- عدم تعطيل الطلب إذا كانت بيانات الإصدار غير صالحة.
- إضافة throttling بسيط حتى لا يتم تحديث قاعدة البيانات مع كل طلب متكرر لنفس المستخدم ونفس الإصدار خلال دقائق قليلة.

### 1.2 تحديث نموذج المستخدم

إضافة حقول آخر إصدار معروف للمستخدم داخل `User`:

- `lastAppVersion`
- `lastAppBuildNumber`
- `lastAppPlatform`
- `lastAppVersionSeenAt`

الغرض من هذه الحقول هو إظهار آخر إصدار استخدمه كل مستخدم بسرعة بدون الحاجة إلى قراءة سجلات التجميع اليومية.

### 1.3 إنشاء تجميع يومي لاستخدام الإصدارات

إنشاء collection جديدة مثل:

`app_version_usage_daily`

الحقول المقترحة:

- `dateKey`: تاريخ بصيغة `YYYY-MM-DD`
- `userId`
- `platform`
- `appVersion`
- `appBuildNumber`
- `firstSeenAt`
- `lastSeenAt`
- `requestCount`

إضافة unique index على:

`dateKey + userId + platform + appVersion + appBuildNumber`

الهدف: حساب المستخدمين الفريدين لكل إصدار يوميًا بدون تخزين كل request كحدث خام.

### 1.4 API للوحة التحكم

إضافة endpoints إدارية تحت:

`GET /admin/user-analytics/app-versions/*`

المسارات المطلوبة:

- `GET /summary`
  - يعرض توزيع المستخدمين حسب الإصدار والمنصة.
  - يدعم فلاتر `platform`, `days`, `status`.
- `GET /trends`
  - يعرض اتجاه الاستخدام اليومي حسب الإصدار.
  - يدعم فلاتر `platform`, `days`, `appVersion`.
- `GET /users`
  - يعرض المستخدمين المرتبطين بإصدار محدد.
  - يدعم `appVersion`, `platform`, `page`, `limit`.

### 1.5 ربط النتائج بسياسة الإصدارات

استخدام نظام `app-config` الحالي لتصنيف الإصدارات إلى:

- `latest`
- `outdated`
- `blocked`
- `unknown`

مثال:

- إذا كان الإصدار يساوي `latestVersion` للمنصة: `latest`
- إذا كان أقل من `minVersion`: `outdated`
- إذا كان داخل `blockedVersions`: `blocked`
- إذا لم يمكن تصنيفه: `unknown`

### 1.6 الفهارس والأداء

إضافة فهارس مناسبة على:

- `User.lastAppVersion`
- `User.lastAppPlatform`
- `User.lastAppVersionSeenAt`
- `app_version_usage_daily.dateKey`
- `app_version_usage_daily.platform`
- `app_version_usage_daily.appVersion`

### 1.7 الاختبارات

- اختبار قراءة الهيدرز من middleware.
- اختبار تجاهل الطلبات بلا إصدار.
- اختبار عدم تعطيل الطلب عند فشل التتبع.
- اختبار تحديث آخر إصدار في المستخدم.
- اختبار إنشاء/تحديث السجل اليومي.
- اختبار endpoints مع الفلاتر والصفحات.
- اختبار تصنيف الإصدارات حسب سياسة `app-config`.

## 2. مهام لوحة التحكم

### 2.1 إضافة تبويب جديد

إضافة تبويب داخل صفحة تحليلات المستخدمين باسم:

`إصدارات التطبيق`

مكانه المقترح: داخل `UserAnalyticsPage`.

### 2.2 API client و hooks

إضافة types و hooks للبيانات التالية:

- `AppVersionSummary`
- `AppVersionTrendPoint`
- `AppVersionUserRow`

الدوال المطلوبة:

- `getAppVersionSummary(filters)`
- `getAppVersionTrends(filters)`
- `getAppVersionUsers(filters)`

### 2.3 واجهة التبويب

التبويب يجب أن يحتوي على:

- بطاقات KPI:
  - إجمالي المستخدمين المرصودين.
  - عدد المستخدمين على آخر إصدار.
  - عدد المستخدمين على إصدارات قديمة.
  - عدد المستخدمين على إصدارات محظورة.
- فلاتر:
  - المنصة: الكل / Android / iOS.
  - الفترة: 7 / 30 / 90 يوم.
  - الحالة: الكل / latest / outdated / blocked / unknown.
- مخطط توزيع الإصدارات.
- مخطط اتجاه يومي للاستخدام.
- جدول تفصيلي للإصدارات.

### 2.4 Drill-down للمستخدمين

عند الضغط على إصدار من الجدول:

- عرض قائمة المستخدمين على هذا الإصدار.
- إظهار:
  - الاسم أو رقم الهاتف.
  - المنصة.
  - رقم الإصدار.
  - رقم البناء.
  - آخر نشاط.
  - آخر وقت تم فيه رصد الإصدار.

### 2.5 الترجمات

إضافة النصوص المطلوبة في:

- `src/core/i18n/locales/ar/users.json`
- `src/core/i18n/locales/en/users.json`

### 2.6 حالات الواجهة

دعم الحالات التالية:

- loading
- empty state
- error state
- refresh
- pagination في قائمة المستخدمين

### 2.7 الاختبارات

- اختبار ظهور التبويب.
- اختبار حالات التحميل والخطأ وعدم وجود بيانات.
- اختبار الفلاتر.
- اختبار فتح قائمة المستخدمين عند اختيار إصدار.

## 3. مهام التطبيق

### 3.1 تحديث خدمة الإصدار

تحديث `AppVersionService` ليخزن:

- `version`
- `buildNumber`
- `platform`

القيم تأتي من `PackageInfo.fromPlatform()`.

### 3.2 تحديث الهيدرز في كل طلب API

تحديث `AppInfoInterceptor` لإرسال:

- `X-App-Version`
- `X-App-Build-Number`
- `X-Platform`

يجب أن تُرسل هذه الهيدرز مع كل طلب API، سواء كان الطلب متعلقًا بالمنتجات أو الطلبات أو الحساب.

### 3.3 ضمان التهيئة المبكرة

التأكد من أن `AppVersionService.init()` يعمل قبل أول طلب API مهم، حتى لا يرسل التطبيق إصدارًا fallback إلا عند الضرورة.

### 3.4 تحديث تسجيل جهاز الإشعارات

تحديث payload تسجيل جهاز الإشعارات ليشمل:

- `appVersion`
- `appBuildNumber`
- `platform`

هذا يجعل بيانات `device_tokens` متسقة مع التحليل الجديد.

### 3.5 الاختبارات

- اختبار أن interceptor يضيف الهيدرز المطلوبة.
- اختبار أن `AppVersionService` يقرأ `version` و `buildNumber`.
- اختبار أن تسجيل جهاز الإشعارات يرسل `appBuildNumber`.

---

## 4. معايير القبول

- عند فتح مستخدم للتطبيق وإرسال أي طلب API مصادق، يظهر آخر إصدار له في لوحة التحكم.
- يمكن للإدارة معرفة عدد المستخدمين على كل إصدار.
- يمكن تصفية النتائج حسب المنصة والفترة وحالة الإصدار.
- يمكن فتح قائمة المستخدمين داخل إصدار محدد.
- لا يتم تخزين كل request كحدث خام؛ التخزين يكون مجمعًا يوميًا.
- الطلبات لا تفشل إذا فشل تتبع الإصدار.
- الإصدارات القديمة قبل إطلاق الميزة تظهر كـ `unknown` حتى يرسل المستخدمون طلبات جديدة.

---

## 5. ملاحظات تنفيذية

- التحليل يقيس المستخدمين المصادقين فقط، لأن ربط الإصدار بالمستخدم يحتاج JWT.
- القياس الأساسي هو آخر إصدار معروف لكل مستخدم.
- الاتجاهات اليومية تعتمد على unique users لكل يوم ولكل إصدار.
- يجب استخدام صلاحيات قراءة التحليلات الحالية مثل `analytics.read` أو صلاحيات الأدمن المعتمدة في المشروع.
- يفضّل إبقاء هذا التحليل داخل نطاق `user-analytics` بدل إنشاء قسم منفصل، لأنه متعلق بسلوك المستخدمين وإصدارات التطبيق.
